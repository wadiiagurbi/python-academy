## Learning Objective

Version your database schema with Alembic autogenerate, upgrade, and downgrade workflows.

## Explanation

Creating tables with `Base.metadata.create_all()` works once, but production needs **migrations** — versioned scripts that evolve the schema without losing data.

**Alembic** is SQLAlchemy's migration tool:

- `alembic init alembic` — scaffolds `alembic.ini` + `env.py`
- `alembic revision --autogenerate -m "add users"` — diffs models vs DB, generates script
- `alembic upgrade head` — applies pending migrations
- `alembic downgrade -1` — reverts one migration
- Each script has `revision`, `down_revision`, `upgrade()`, `downgrade()`

For async SQLAlchemy, `env.py` uses `async_engine_from_config` and `run_sync`.

## Why It Matters

Manual `ALTER TABLE` is error-prone and untracked. Migrations give you code review, rollback, CI/CD integration, and identical schemas across dev/staging/prod. Every production FastAPI + SQLAlchemy app uses them.

## Example

```python
# versions/a1b2c3_add_users.py (generated)
revision = "a1b2c3"
down_revision = None

from alembic import op
import sqlalchemy as sa

def upgrade():
    op.create_table(
        "users",
        sa.Column("id", sa.Integer, primary_key=True),
        sa.Column("email", sa.String, unique=True, nullable=False),
    )

def downgrade():
    op.drop_table("users")
```

## Code

```python
# env.py — async Alembic setup (excerpt)
# Place in alembic/env.py after `alembic init alembic`
import asyncio
from sqlalchemy.ext.asyncio import async_engine_from_config
from sqlalchemy import pool
from alembic import context

# Import your models so autogenerate sees them!
# from myapp.models import Base
# target_metadata = Base.metadata
target_metadata = None  # replace with your Base.metadata

config = context.config

def do_run_migrations(connection):
    context.configure(connection=connection, target_metadata=target_metadata)
    with context.begin_transaction():
        context.run_migrations()

async def run_migrations_online():
    connectable = async_engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    async with connectable.connect() as connection:
        await connection.run_sync(do_run_migrations)
    await connectable.dispose()

# Typical CLI workflow (run in terminal):
# alembic revision --autogenerate -m "add posts table"
# alembic upgrade head
# alembic history
# alembic downgrade -1
```

```python
# Example hand-edited migration: add index + non-null column safely
from alembic import op
import sqlalchemy as sa

revision = "d4e5f6"
down_revision = "a1b2c3"

def upgrade():
    # 1. Add nullable first (safe for existing rows)
    op.add_column("posts", sa.Column("slug", sa.String(length=200), nullable=True))
    # 2. Backfill in batches in production!
    # op.execute("UPDATE posts SET slug = lower(replace(title, ' ', '-')) WHERE slug IS NULL")
    # 3. Add index
    op.create_index("ix_posts_slug", "posts", ["slug"], unique=True)

def downgrade():
    op.drop_index("ix_posts_slug", table_name="posts")
    op.drop_column("posts", "slug")
```

## Code Explanation

`target_metadata = Base.metadata` lets autogenerate compare models to the live DB — without importing models, autogenerate sees nothing.
`async_engine_from_config` reads `sqlalchemy.url` from `alembic.ini`; `run_sync` bridges async connection to Alembic's sync API.
Migration pattern for new columns: add nullable → backfill → set NOT NULL. Adding a NOT NULL column without default on a populated table fails.
`upgrade()` must be mirrored by `downgrade()` for safe rollback.

## Common Mistakes

- Forgetting to import models in `env.py` — autogenerate produces empty migrations
- Editing an already-applied migration instead of creating a new one — environments diverge!
- Adding `nullable=False` column without server default on existing table — upgrade fails
- Committing without running `upgrade head` locally — untested migrations break CI
- Using `create_all()` in production alongside Alembic — pick one (Alembic)

## Best Practices

- One logical change per revision with clear `-m` message
- Always review autogenerated scripts — autogenerate misses renames, data migrations, partial indexes
- Test `upgrade` and `downgrade` on a copy of prod data
- Set `sqlalchemy.url` via env var in `env.py` (do not commit passwords)
- Run migrations in deploy pipeline before starting new app version

## Exercise

Add a `created_at` timestamp column to a `users` table via a new Alembic revision. Write `upgrade()` and `downgrade()` with a server default so existing rows succeed.

## Solution

```python
from alembic import op
import sqlalchemy as sa

revision = "add_created_at"
down_revision = "d4e5f6"

def upgrade():
    op.add_column(
        "users",
        sa.Column("created_at", sa.DateTime(), server_default=sa.func.now(), nullable=False),
    )

def downgrade():
    op.drop_column("users", "created_at")
```
